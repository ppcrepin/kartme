KartMe · Comment on va travailler

Architecture d'exécution

Une équipe d'agents spécialisés que je coordonne, avec toi comme décideur final. Ce modèle est pensé pour rester stable et cohérent d'une session à l'autre : il vivra dans le repo et sera relu au démarrage de chaque reprise.

1L'équipe & la hiérarchie

TOI — Product Owner
Vision, priorités, validation de toute décision stratégique. Rien de stratégique n'avance sans ton feu vert.
MOI — Orchestrateur (Claude Code)
Je découpe le travail, dispatche aux agents, assemble, garde la cohérence avec le cahier, et te reporte. Je code peu moi-même : je coordonne et j'arbitre.
Backend
Supabase : schéma, migrations, logique Elo, API, notifications, stockage
Frontend
Expo (RN + Web) : écrans, composants, navigation, i18n, intégration API
Design / UX
Design system Rosso Corsa, maquettes, iconographie, cohérence UX — en amont du Frontend
Sécurité / Infra
RLS, RGPD, anti-triche, infra & coûts, déploiement / CI
Reviewer
Revue de code adversariale : bugs, sécurité, simplicité, cohérence. Avant tout merge
Testeur (QA)
Tests (Elo, intégration, e2e), exécution réelle, vérif des chiffres. Garant du Definition of Done

Équipe de 6 agents. Reviewer et Testeur formalisent l'agent « challenge » déjà utilisé systématiquement : rien ne passe sans audit adversarial + vérification.

2Le pipeline, par fonctionnalité

1
Cadrage — j'extrais du cahier les critères d'acceptation, je découpe en tâches backend + frontend, je te soumets les points stratégiques.
2
Design/UX — si l'UI est concernée : maquette + décisions visuelles validées avant le code.
3
Build — Backend et Frontend travaillent (en parallèle quand indépendants) sur une branche dédiée au lot.
4
Revue — le Reviewer audite le diff (bugs, sécurité, cohérence). Corrections en boucle jusqu'au vert.
5
Test — le Testeur écrit/exécute les tests et exerce réellement les flux (pas juste « ça compile »). Vérifie les chiffres Elo.
6
Assemblage & rapport — je vérifie la cohérence globale, je te fais un rapport concis, et je pousse une fois tout vert (PR seulement si tu la demandes).

Orchestration : workflows structurés (pipeline déterministe design → build → review → test) dès le départ, pour une exécution reproductible. Tu as donné ton accord permanent à l'orchestration multi-agents sur ce projet.

3Le portail de décision — ce qui remonte à toi

Tu as demandé « peu de liberté » : par défaut, en cas de doute, je remonte.

◆ Stratégique → ta validation
  • Périmètre & priorités de la roadmap
  • Tout ce qui est visible par l'utilisateur (écrans, flux, textes clés)
  • Règles du jeu : Elo, grades, badges, cycle de course
  • Nouvelle dépendance ou tout ce qui a un coût
  • Sécurité, RGPD, données personnelles
  • Marque, nom, identité
  • Tout écart au cahier des charges
○ Tactique → je décide & documente
  • Structure du code, nommage, découpage
  • Refactors internes sans impact produit
  • Choix de libs mineures (sans coût / sans risque)
  • Détails d'implémentation, optimisations
  • Organisation des tests
  • Corrections de bugs conformes au cahier

4Cohérence entre les sessions

Pour qu'à chaque reprise on garde la même architecture, tout vit dans le repo. Toute session lit ces fichiers en premier :

  • AGENTS.md — ce document d'architecture d'exécution (rôles, pipeline, portail de décision, conventions). Lu en premier à chaque session.
  • docs/cahier-des-charges.md — la source de vérité produit.
  • docs/roadmap.md — la roadmap + l'état d'avancement (statut par lot), mise à jour à chaque session.
  • docs/decisions.html — le registre des décisions déjà tranchées.
  • Git : une branche par lot, commits clairs, audit Reviewer+Testeur avant merge, PR uniquement sur ta demande.

5Definition of Done — rien n'est « fini » sans ça

✓Conforme au cahier et aux critères d'acceptation du lot
✓Reviewer : aucun bug bloquant, code cohérent et simple, sécurité OK
✓Testeur : tests passent + flux exercé réellement + chiffres Elo vérifiés
✓Accessibilité respectée (couleur + signe, contrastes, focus clavier)
✓Docs à jour (cahier / roadmap / décisions) et poussé sur GitHub

6Comment je te reporte

À chaque étape clé : un résumé concis (fait / en cours / bloqué), et les décisions stratégiques présentées en questions cliquables — comme depuis le début. Aucune décision stratégique n'avance sans ton clic. Tu peux reprendre le fil à tout moment : l'état est toujours dans le repo.
